# Ghost Shell (the dotfiles repo)

Arch Linux + Hyprland dotfiles, deployed with GNU Stow; on GitHub as RazerGhost/ghost-shell, checked out at ~/Projects/ghost-shell on the laptop (it was ~/dotfiles until 2026-10-31). The `ghost` command (`bin/.local/bin/ghost`) runs the setup.

- Each top-level directory except `modules/`, `system/`, `tests/`, `docs/`, `machines/` (module lists per machine, `ghost install --machine <name>`) and `migrations/` is a Stow package mirroring `$HOME`, e.g. `hypr/.config/hypr/hyprland.lua`. Don't move or rename these while the desktop runs from them: the links break for a moment (Hyprland once lost hyprland.lua that way). Only the packages in `folded_packages` (`modules/lib.sh`: folders only this repo writes into) are linked as whole folders; the rest file by file, so other programs' files never land in the repo, and a file added to them needs `ghost install core` to be linked (`tests/stow_test.sh`).
- `modules/<name>/` holds one part of the setup each: its packages (`packages.txt` for pacman, `aur.txt` for paru, and `packages.sh` printing the ones that depend on the hardware, like the system module's NVIDIA packages) and its setup (`setup.sh`, re-runnable). The modules are core, system, snapshots, apps, dev, gaming, discord, spotify, zen, haunt, capture, phone, proton, calendar, llm and wave3; `modules/lib.sh` (`step`, `fail`, `hw`, `clone_or_pull`, `clone_at`, `json_edit`, `module_autostart`) is shared. New packages and setup steps go in the module they belong to (or a new one, added to `all_modules` and `about` in `bin/.local/bin/ghost`). The shared configs never start or require a program only one module installs: a program Hyprland starts goes in `modules/<name>/autostart.lua`, which the module's setup links into `~/.config/hypr/autostart.d/` (`module_autostart`).
- `ghost` (`bin/.local/bin/ghost`, a Stow package) runs everything: `install [module...] [--theme X]`, `update` (refuses with uncommitted changes rather than stashing), `theme`, `migrate`, `doctor`, `modules`, `keybinds`. `install.sh` is only the first-run bootstrap for `ghost install`. A machine picks its modules in `~/.config/ghost/modules` (not in git); without it, all.
- Setting the wallpaper and colors goes through `matugen/.config/matugen/wallpaper.sh`, used by `ghost theme`, the core module and the shell's wallpaper picker. matugen hooks only deliver colors; setting an app up belongs in its module's `setup.sh`.
- There is no login screen: greetd (`system/etc/greetd/config.toml`, installed by the system module) starts the session at boot and after every logout with `GHOST_AUTOLOGIN=1`, and the shell locks it at once (`lock/Lock.qml`; `hyprland.lua` holds the keybinds back until then). The lock screen is the desktop, locked: its wallpaper and desktop widgets, with the island asking for the password.
- Machine-local overrides, gitignored and loaded last: `hypr/.config/hypr/local.lua`, `ghostty/.config/ghostty/local`, `~/.config/zsh/local.zsh` (zsh, the login shell since 2026-11-05), `fish/.config/fish/conf.d/local.fish`. Machine-specific things go there, not in the repo's files.
- `system/` is not a Stow package: it mirrors `/` and the system module (`modules/system/setup.sh`) copies its files into place with `sudo install` (udev rule, greetd config, mkinitcpio drop-ins); it also appends `plymouth.enable=0` and a quiet console to `/etc/default/limine` (no splash: the session's lock screen is the first thing drawn).
- matugen (`matugen/`) generates colors from the wallpaper for Quickshell, Hyprland, Ghostty, GTK, Yazi, Spotify, Discord, MangoHud, Zed, Steam and Zen (list in its `config.toml`). Templates are committed; generated output is gitignored.
- Browser is Zen (`zen-browser-bin` from the AUR), not Firefox. Use it wherever a browser is launched or set as default.
- Hyprland and Quickshell run on the laptop and the desktop (both CachyOS; `hostnamectl` says which one a session is on). A session on either can run and test changes directly (`qs`, `hyprctl`, `journalctl`), and hands the user a test checklist for the other machine when a change depends on its hardware.
- Commit and push after each phase or fix; the user may pull on another machine.
- `tests/` holds QML tests (not a Stow package). Run them with `QT_QPA_PLATFORM=offscreen /usr/lib/qt6/bin/qmltestrunner -input tests`, the tiling layout's Lua test with `lua tests/tiling_test.lua`, the calendar setup's with `bash tests/calendar_test.sh` (stand-in tools, a scratch home), the terminal greeting's with `bash tests/greeting_test.sh`, the hardware detection's with `bash tests/hw_test.sh` (stand-in sysfs), and the hardware fixes' with `bash tests/hardware_fixes_test.sh`, and `ghost migrate`'s with `bash tests/migrations_test.sh`.
- `setup.sh` scripts describe how a machine should be now. Undoing what an earlier version installed is a migration: `migrations/<date>-<what>.sh`, run once per machine by `ghost migrate` (and every install and update), safe on a fresh machine (`migrations/README.md`).
- Hardware differs between machines (the laptop: hybrid AMD + RTX, battery, lid; the desktop: RTX drives the screens, a small Ryzen iGPU beside it). Only `bin/.local/bin/ghost-hw` tests hardware; configs, modules and scripts ask it (`hw <question>` in `modules/lib.sh`), never `lspci`, a vendor's card or a board name directly. A fix for one machine's hardware is a file in `modules/system/hardware/` that starts with its check.
- Files use LF line endings (enforced in `.gitattributes`), even when edited on Windows.
- `ROADMAP.md` has the phase plan, decisions and open issues. Update it when a phase finishes or a decision changes.
- `NOTES.md` has the verified Quickshell/Hyprland API facts and how to test on the laptop. Read it before using an API it might cover, and add facts you verify.
- `docs/index.md` maps every feature and rule to its files, plus the `ghost` commands, IPC targets and Settings pages. Look there first to find where something lives, and update it when a feature, IPC function, Settings page, module or rule is added, moved or removed.
